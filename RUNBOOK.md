# Netkit maintainer runbook

Netkit is a CLI and container image distributed to users, not a hosted service.
There is no centrally operated Netkit production deployment or service on-call.
Repository maintainers own release quality; users own their installations,
network exposure, infrastructure, and any upstream services they call.

## Validate a release

Run `make test`, `make e2e`, and `make test-docker-dashboard` before publishing.
The Docker check verifies the non-root runtime user, embedded dashboard,
JavaScript assets, and same-origin health endpoint. The tag workflow also checks
an image built with the `/netkit` URL prefix before publication.

The Release on Tag workflow publishes platform binaries and checksums to GitHub
Releases and images to Docker Hub. Build/test jobs have read-only repository
access. The publishing job needs `contents: write` to publish releases; Docker
Hub uses its own credentials and needs no GitHub `packages: write` permission.
E2E failure reporting alone needs `issues: write`. Platform Doctor currently
flags these explicit job permissions even though they are necessary.

## Diagnose a local installation

Start the CLI with `netkit serve --admin-port 8081`, then check:

```sh
curl --fail http://localhost:8081/healthz
curl --fail http://localhost:3000/api/admin/healthz
```

Inspect terminal output (or `docker logs CONTAINER`) for bind errors, upstream
connection failures, and dashboard configuration errors. Confirm the configured
ports and `NETKIT_DASHBOARD_BASE_PATH`. Keep proxy and admin access on trusted
networks. Request history is in memory and disappears when the process restarts;
redact captured credentials and bodies before sharing diagnostic reports.

## Rollback a CLI or container installation

Rollback means restoring a user's previous working version, not reverting a
central service deployment. Record the current version, startup arguments, and
previous working version before upgrading.

For a CLI installed from a release:

1. Stop the running Netkit process using the same terminal or service manager
   that started it. This interrupts proxy connections and clears request history.
2. Download the correct OS/architecture binary and `checksums.txt` from the
   previous known-good GitHub release. Verify the binary against its checksum
   (`sha256sum` on Linux or `shasum -a 256` on macOS).
3. Replace the installed executable, make it executable on Unix, and restart
   with the same arguments. For example, after downloading and verifying the
   macOS ARM64 binary, for an installation in `$HOME/.local/bin`:

   ```sh
   install -m 755 ./netkit-darwin-arm64 "$HOME/.local/bin/netkit"
   "$HOME/.local/bin/netkit" serve --admin-port 8081
   ```

For a container, restore the previous image tag or digest in the user's Docker,
Compose, or orchestrator configuration and recreate the container with the same
ports, environment, and arguments. Avoid `latest` when reproducible upgrades and
rollback matter. Check `/healthz`, dashboard loading, and a request to a known
upstream after restarting either installation.

If a published version is broken, maintainers should document the affected
version and recommend the previous working version, revert or fix the regression
in a pull request, and publish a new patch release. Do not move an existing tag
or overwrite its artifacts as a rollback procedure.

## Budget and cost alerts: applicability

Netkit has no hosted-service cloud budget, billing account, or customer spend
limit to configure. Installing the CLI does not provision cloud infrastructure.
Users are responsible for any hosting, network egress, and paid upstream API
charges generated by their own requests. Netkit does not enforce those budgets.

Repository distribution can still consume GitHub Actions minutes/artifact
storage and Docker Hub allowances. The repository/billing account owner should
review those providers' usage before enabling paid capacity and after unexpected
build activity. No dollar budget or live cost alert is configured by this
repository, and this document does not claim otherwise. If paid usage is enabled,
the account owner must choose a monthly cap and configure provider notifications
at 80% and 100% of that cap. At 80%, review repeated builds and artifact retention;
at 100%, pause discretionary builds until the owner approves further spending.

This is maintainer guidance, not evidence that external billing settings or
notifications have been enabled. A cloud-budget finding against this CLI should
be treated as a check-applicability limitation, not as a missing production
control.
